# PLATO to CUDA/PTX: Does the Architecture Port?
## A sourced research report on PLATO/TUTOR internals, their mapping to modern NVIDIA GPU programming, and the current state of the art for GPU-resident multi-client simulation

*Research date: 27 October 2026. British English.*

**How to read this report.** Claims are labelled throughout:

- **[VERIFIED]** — stated by a source cited at the end of the sentence/paragraph, read during this research (live-verified pages are noted in Sources).
- **[INFERENCE]** — the author's reasoned mapping from verified facts; no source states it in this form.
- **[SPECULATION]** — plausible but untested or unsourced; treat as a hypothesis to benchmark, not a fact.

**Short answer.** The thesis is *half right, and the half that is right is not quite the half stated*. PLATO's **data architecture** — small fixed-size per-client state arrays indexed by client ID, a small shared "common" per shared world/lesson, fixed allocations, no dynamic allocation in the hot path, event-driven service, and state tiered between a small fast memory and a larger slower electronic memory — ports to CUDA almost one-for-one, and in places the GPU version is strictly better (real atomics, real parallelism, shared memory that is genuinely shared). PLATO's **execution architecture**, however, does *not* port naturally: PLATO was an event-driven, latency-oriented, sequentially-interpreting timesharing system whose clients were mostly idle humans typing at 1,260 bit/s, and whose "dynamic feel" came from per-keypress immediacy and a display that needed no refresh — not from a continuous tick. A GPU is a throughput machine that hides latency with thousands of homogeneous threads and serialises exactly the kind of irregular per-client control flow that TUTOR specialised in. At the builder's stated scale — *dozens* of clients — the GPU is so underloaded that the honest engineering question inverts: not "can a GPU do what PLATO did?" (trivially yes, by orders of magnitude) but "does a *persistent* kernel buy anything over short launched kernels or CUDA Graphs at this scale, and what does it cost in preemption, power, and failure modes?" The published evidence on persistent workers is mixed, and the state-of-the-art GPU agent framework (FLAME GPU) pointedly does **not** use a persistent kernel: it uses one short kernel per agent function, with agents sorted into homogeneous state lists. That contrast is the single most useful finding in this report.

## 1. PLATO/TUTOR internals, concretely

### 1.1 What the system was

[VERIFIED] PLATO (Programmed Logic for Automatic Teaching Operations) was built at the University of Illinois Computer-based Education Research Laboratory (CERL) from 1960; PLATO III ran on a CDC 1604 and supported up to 20 terminals; PLATO IV moved to CDC Cyber (6000-series) hardware. Sources: Illinois Grainger College history, https://grainger.illinois.edu/news/magazine/plato ; PLATO system survey, https://en.wikipedia.org/wiki/PLATO_(computer_system)

[VERIFIED] By July 1975 the Illinois PLATO IV system had **950 terminals installed and as many as 480 simultaneously active**, on a CDC Cyber with "electronic swapping memory", served by a "fast-response operating system and a compiler and executor for lesson materials written in the TUTOR language". The designed-for capacity was ~1,000 terminals on one TV channel, and later recollections and Illinois's own history put the mature system at up to 1,000 simultaneous users and ~600 concurrent logged-in terminals on a dual-mainframe configuration c. 1977. Sources: Sherwood & Stifle, *The PLATO IV Communications System*, CERL Report X-44, June 1975 (verified live), https://archive.org/download/micro_IA41153028_0257/micro_IA41153028_0257.pdf ; Grainger, above; first-hand recollection (lower weight, see Sources), https://classiccmp.org/mailman3/hyperkitty/list/test-drb@ccmp.vtda.org/message/THQXWWNK7XCFQLDT2XGEM2BHMLIUQ7R7/

### 1.2 Scheduling: an event list, not a tick

This is the point the thesis most often gets wrong, so it is worth being precise.

[VERIFIED] On PLATO III, the sequence was interrupt-and-service: "a student pushing a key on his keyset… interrupts the computer, which pauses just long enough to add the key and its accompanying terminal identification number to a list. Eventually the computer services this request, at which point the terminal identification number is used to reference the correct student bank." The executor then examined the lesson material and the student's bank to decide what to do for *that* student. There were **no disk accesses during lesson presentation** — lesson material and per-student pointers/counters resided in core — which is explicitly credited for response faster than typical multi-terminal systems. Source: *The PLATO System and Science Education* (CERL-era text, via archive.org), https://archive.org/stream/micro_IA41153144_0492/micro_IA41153144_0492_djvu.txt

[VERIFIED] On PLATO IV, every keypress still passed through the central computer — there was **no local echo** — so that key meaning was fully redefinable in context (a key could produce a Cyrillic character or a line drawing). Measured average response was **125 ms (one-eighth of a second)**, of which *half was hardware* (serial transmission, buffering in interface equipment) and *half software, "mainly input and output polling and buffering; the actual processing is typically a few milliseconds and only a fraction of a millisecond for simple key echoing"*. The design requirement driving the whole communications system was an average response **under 0.25 s**, which ruled out store-and-forward and terminal polling designs. Each terminal was guaranteed 1,260 bit/s in each direction at all times; up to 32 terminals were concentrated by a Site Controller, and 32 Site Controllers fed a Network Interface Unit — 1,008 terminals per TV channel. Source: Sherwood & Stifle 1975, URL above.

[VERIFIED] Headroom was a deliberate policy: PLATO IV design material states a reserve "of the order of 40 percent of the total available time" was set aside above average load specifically so that typical waiting time stayed under 0.2 s. Source (via archive.org progress report): https://archive.org/download/micro_IA41153028_0242/micro_IA41153028_0242.pdf

[INFERENCE] So PLATO's scheduler is best described as a **central, event-driven, work-conserving service loop with admission by fixed allocation and a large deliberate idle reserve** — closer to a modern event-loop server (or a device-side work queue drained by a resident worker) than to a fixed-rate game tick. Work arrived as discrete keypress events; the machine ran a short burst of TUTOR for one user; then it waited. Continuous-feeling multi-user programs had to be built *on top of* that: players in *Empire* requested screen updates manually and the display also refreshed on a slow timer (recalled as ~5 s; anecdotal, low confidence), rather than the system pushing frames. Source for the anecdote: https://classiccmp.org/mailman3/hyperkitty/list/test-drb@ccmp.vtda.org/message/RQYA33BNOKC6IUITE4CXP6L5OCDIEU3O/

### 1.3 TUTOR's execution model: the lesson/unit/judging machine

[VERIFIED] TUTOR lessons are organised into **units**. In a unit, "regular" commands execute until an `-arrow-` command, which waits for a student response; then only **judging** commands execute, scanning `-answer-`/`-ansv-`/`-wrong-`/`-match-` etc. tags against the response until one matches, whereupon the regular commands following that judging command run until the next judging command, `-arrow-`, or `-unit-`. It is, in modern terms, a small state machine alternating *present → wait → judge → respond*, with the student's position held in his bank. Sources: *Introduction to TUTOR* / *The TUTOR Language* (Sherwood, 1977), https://vpython.org/contents/cTsource/The_TUTOR_Language_1977.pdf and flow-diagram text at https://archive.org/download/micro_IA41153028_0246/micro_IA41153028_0246.pdf

[VERIFIED] Lessons were **condensed** (compiled) before use — system documentation and later CYBIS material refer to lessons re-condensing when edited and to the compiled binary being deleted to force re-condensation — and then run by the central **executor** against per-user state. (Index-only for the condense detail.) Source: CYBIS Operation and Usage Manual, https://p.xn--akfrster-p4a.de/cgi-bin/gopher?u=gopher://gopher.unixwire.com/d/dtcyber/cybis/CYBIS_Operation_and_Usage_Manual.pdf

[INFERENCE] TUTOR execution per event was therefore: fetch the condensed code for the unit the user is in, interpret/execute a *short, bounded* burst against that user's variables and the lesson's common, emit output, and stop at the next wait. Nothing ran "for" a user between his keypresses except shared programs other users were driving.

### 1.4 Per-user state: the student variables / student bank

[VERIFIED] Each user process had a **private data segment of exactly 150 words** — the "student variables", addressed `n1`–`n150` as integers or `v1`–`v150` as floating point (60-bit words on PLATO IV, matching the CDC 6600 family). These values were **persistent: they followed the individual user from session to session** (preserved in the student record on disk for "student"-type users). Where 150 were insufficient, a `storage` command added up to 1,000 further words, held in swap space only and mapped in with commands such as `-stoload-`. A full per-terminal status record was larger: one contemporary analysis lists 150 words of student variables **plus ~250 words of PLATO status data** (lesson, student and terminal status). On PLATO III the whole per-student bank was 300 words, containing (in that generation) 139 TUTOR variables, answer storage, and the pointers marking the student's place in the lesson. Sources: TUTOR reference summary, http://staroceans.org/wiki/A/TUTOR and https://en.wikipedia.org/wiki/TUTOR_(programming_language) ; DTIC TUTOR minicomputer study (index), https://archive.org/stream/DTIC_ADA005782/DTIC_ADA005782_djvu.txt ; PLATO III text, URL in §1.2.

[INFERENCE] Note the shape: **fixed-size, fixed-count, flat, unnamed-by-default arrays, indexed by slot, with symbolic names layered on top by `define`**. There is no heap, no per-user allocation, no variable-length state in the hot model. Every user's footprint is known at system build time, so capacity planning is arithmetic: *N* users × ~400 words.

### 1.5 Shared state: TUTOR "common blocks"

[VERIFIED] A lesson could attach **one shared region of up to 1,500 words** with the `common` command, addressed `nc1`–`nc1500` / `vc1`–`vc1500`, **shared by all users of that lesson**. Two kinds existed: *unnamed temporary* common, created when a lesson came into use and deallocated when it became inactive; and *named* common, backed by a block of a lesson (a disk file) — in CYBIS terms, common lived in ECS while in use, was **checkpointed back to disk** periodically, and was normally brought into central memory (`-comload-`) to be manipulated, with `-transfr-` available to write the ECS copy directly. Fewer than 25% of lessons used COMMON at all, in the DTIC survey. Sources: TUTOR summary and CYBIS manual, URLs above.

[VERIFIED] Common was the entire inter-user mechanism, and it demonstrably sufficed for the famous social software: PLATO IV's shared-memory construct "allowed TUTOR programs to send data between various users" and "was used both for chat-type programs, as well as the first multi-user flight simulator". Multi-user artefacts built on it included Talkomatic (1973; initially six channels/rooms of five), *Empire* (30-player real-time space simulation, c. 1974), *Spasim* (32-player), and *Avatar* (60-player MUD, c. 1978). Sources: https://en.wikipedia.org/wiki/PLATO_(computer_system) ; Woolley (below).

[VERIFIED] Talkomatic's feel is documented by its co-author: characters were **transmitted instantly as typed**, each participant in his own horizontal window, up to five active participants per channel plus any number of read-only monitors; "seeing messages appear literally as they were typed made the conversation feel much more alive than in line-by-line chat programs". It logged over 40 hours of use per day soon after launch. Source: Woolley, "PLATO: The Emergence of On-Line Community" (1994), Talkomatic chapter (verified live), https://liz.nl/plato04.htm

[INFERENCE] Crucially, common had **no concurrency-control problem worth the name**, because the executor serviced users one burst at a time: a user's TUTOR burst saw a stable common, modified it, and finished before the next user's burst ran. Shared memory without parallel writers is just memory. This is the assumption that silently breaks in the GPU port (see §2).

### 1.6 ECS: the two-tier memory that made it possible

[VERIFIED] PLATO IV eliminated swapping to mechanical disk/drum and used **CDC Extended Core Storage (ECS)** as an electronic swapping memory, with "a transfer rate one hundred times greater and an access time one thousand times shorter" than disks or drums — explicitly credited with making fractional-second response to hundreds of terminals possible. The design placed **student banks and lesson material in ECS**; "when needed, portions or all of a particular student bank and related lesson material can be rapidly transferred from ECS into the computer's central memory". Planned ECS was two million 60-bit words — enough for **4,000 student banks plus 250 hours of lesson material**. Sources: Sherwood & Stifle 1975; PLATO III/IV text, URLs above.

[VERIFIED] Recollection from a system programmer on the later dual-mainframe Illinois system: "PLATO made extensive use of ECS, swapping per-terminal state and programs in and out of ECS for fast interactive service. ECS was also where most I/O buffers went, with PPUs doing disk and terminal I/O from/to ECS rather than central memory." (First-hand mailing-list recollection; treat as corroborating, not primary.) Source: classiccmp thread, URL in §1.1.

### 1.7 The CDC Cyber's peripheral processors (PPUs)

[VERIFIED] The CDC 6600/Cyber line split labour by design: a fast 60-bit central processor (CP) for user computation, and **ten peripheral processors** — full small computers (12-bit, each with its own 4,096-word memory) that ran **nearly all of the operating system plus I/O**, "thus leaving the full power of the Central Processor available for user programs". The ten PPs were themselves virtual: one shared execution unit (the "slot") served ten register sets in round-robin ("barrel") fashion, a full rotation taking 1 µs — an early barrel (hardware-multithreaded) processor. Later Cyber models offered 10–20 PPUs. Sources: https://en.wikipedia.org/wiki/CDC_6600 ; University of Iowa retrocomputing notes, http://homepage.cs.uiowa.edu/~dwjones/retro/notes/19.shtml

[INFERENCE] Three separate ideas are bundled in "the PPUs", and they port differently (§2): (a) *offload* — weak helpers do I/O and housekeeping so the strong processor never waits; (b) *concentration* — the site-controller/NIU tree aggregated 1,008 slow terminals into few fast channels; (c) *barrel sharing* — many independent slow instruction streams timesharing one execution unit in fixed round-robin, which is structurally a warp scheduler's ancestor, not a coprocessor's.

### 1.8 The display: the other half of "feels dynamic"

[VERIFIED] The PLATO IV terminal's plasma panel (512×512) had **inherent memory**: "the panel is both a display and a storage device. Once a pixel is lit, it stays lit until the person at the terminal requests new information" — so unlike a CRT it needed **no refresh memory and no refresh traffic**, and the terminal electronics "need operate only fast enough to stay ahead of the incoming data" at 1,200 bit/s input. Sources: University of Illinois ECE, https://ece.illinois.edu/news/2541 ; Stifle, *The PLATO IV Student Terminal*, https://archive.org/download/micro_IA41153028_0259/micro_IA41153028_0259.pdf

[INFERENCE] This is routinely underweighted in retellings. PLATO could afford to send only *deltas* (a character, a line, a selective erase) down a 1,260 bit/s straw because the display held the frame for free. "Dynamic" on PLATO meant: **immediate echo, incremental update, persistent picture** — at an average 125 ms response, of which only a few milliseconds were compute. Brian Dear's *The Friendly Orange Glow* (2017) is the standard narrative history and makes the same responsiveness point — Bitzer's requirement that input be processed and returned "within tens of milliseconds" is quoted in reviews of the book — but note this research read reviews and excerpts of Dear, not the book itself; the primary numbers above come from CERL's own reports, which are stronger evidence anyway. Review source: https://sohkamyung.github.io/reviews/nonfiction/2024/20241218-FriendlyOrangeGlow.html

## 2. The mapping, mechanism by mechanism

### 2.0 Summary table

| PLATO mechanism | Proposed CUDA analogue | Verdict | One-line reason |
|---|---|---|---|
| Student bank: 150 fixed words/user, indexed by terminal ID | Per-client state arrays in global memory, indexed by client ID | **Holds, strongly** | Same fixed-footprint, slot-indexed design; GPU adds tiering (see ECS row) |
| Student bank swapped ECS→CM on service | Stage hot client/room state global→shared (or registers) per tick | **Holds** | ECS/CM *is* the global/shared hierarchy, 50 years early |
| Lesson common (≤1,500 words, all users of a lesson) | Room state in **shared memory, room = thread block**; larger commons in global + atomics | **Holds at room scale; strains beyond one block** | 1,500×8 B = 12 KB fits shared memory easily; cross-block sharing loses the free serialisation PLATO had |
| Executor services one user's burst at a time (no parallel writers) | Atomic/serialised updates, double-buffered message lists, or single-writer rules | **Strains — the hidden assumption** | PLATO never solved parallel contention; the GPU port must, explicitly |
| Keypress event list + service bursts | Device-side ring/event queues drained by resident workers; host→device pinned ring buffers | **Holds** | This is exactly the persistent-kernel work-queue pattern now used in LLM serving (§3) |
| No continuous tick; timers/manual refresh for games | Event-first scheduling; tick only dirty rooms | **Holds as design advice; contradicts a naive "always tick everything" floor** | PLATO's economy came from *not* ticking idle clients |
| TUTOR unit/judging state machine per user, arbitrary branching | Thread-per-client interpreter | **Strains badly** | Per-client irregular control flow = intra-warp divergence; paths serialise |
| Same, but clients bucketed by unit/state | Sort/bucket clients by programme-state (FLAME GPU's state lists); or **warp-per-client** | **Holds if you pay for the bucketing or the lanes** | Homogeneity is manufactured, not free |
| PPUs: OS + I/O offloaded from CP | Host CPU + streams, copy engines/TMA, dedicated I/O warps (warp specialisation) | **Holds, with roles inverted** | On the GPU the "helper" (host) is the latency-strong party and the "main" processor is throughput-strong |
| PPU barrel: 10 streams, one slot, round-robin | SM warp schedulers timesharing warps | **Holds as analogy, not as a design lever** | You get this for free; it is why a spinning persistent kernel still lets other warps run |
| Site controllers concentrating 32 terminals | One warp / one lane-leader aggregating 32 clients' I/O; batched host transfers | **Holds, pleasingly literal** | 32 terminals per concentrator ≈ 32 lanes per warp is coincidence, but batching-by-32 is real |
| Plasma panel: inherent memory, delta-only output | Client-side rendering / retained frame; GPU sends deltas, not frames | **Holds, and the GPU neither helps nor hinders** | The trick lives at the client/protocol layer, not in the kernel |
| Named common checkpointed ECS→disk; student vars persist across sessions | Checkpoint room+client state to host at tick boundaries; GPU memory treated as volatile cache | **Holds, and is mandatory** | Device memory is ECS, not disk: a kernel exit/crash loses it unless checkpointed |
| 40% reserve so response stays <0.2 s | Cap per-tick work; budget + defer; keep SM headroom | **Holds** | The cheapest latency mechanism in either era |

### 2.1 Per-client state arrays → thread-per-client vs warp-per-client

[VERIFIED] CUDA executes threads in warps of 32 sharing an instruction stream (SIMT); when threads in a warp take different paths, the paths are executed serially with inactive lanes masked. NVIDIA's programming guide frames the whole architecture as latency *hidden by many warps*, with transistors spent on arithmetic throughput rather than cache/control. Sources: NVIDIA CUDA Programming Guide, https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/writing-cuda-kernels.html ; divergence/SoA treatment in §2.3 references.

[INFERENCE] **Thread-per-client** is the right layout when all clients run the *same* short tick code with data-dependent *values* but uniform *control flow* (integrate, decay, sense neighbours, apply a queued event of a common type). Then a warp of 32 clients is one instruction stream and the mapping is essentially perfect — and at "dozens of clients" the entire client population is **one or two warps**, which is also the mapping's embarrassment: there is no parallelism left to hide the several-hundred-cycle global-memory latency, so per-tick latency is dominated by a handful of dependent memory accesses. That may still be microseconds and entirely fine — but it must be measured as a *latency* problem, not assumed away as a throughput problem.

[INFERENCE] **Warp-per-client** is the right layout when per-client behaviour is *irregular* — an interpreter loop, a judging scan, a behaviour tree — because divergence *between* warps costs nothing: each warp has its own instruction stream. Warp-specialisation literature makes the same point in reverse: assigning whole warps to whole jobs is "a real, persistent divergence for the block's lifetime… at warp granularity, there is no intra-warp penalty". Source (index): https://www.aicassindra.com/blogs/gpu/gpu_warp_specialization.html . The cost is 32 lanes per client; at 64 clients that is 64 warps ≈ 2,048 threads — one modest block-count, still small for a modern SM array, and the 32 lanes can be *used* (parallel judging over candidate answers, parallel scan of a room's message list, ballot-compacted event handling) rather than merely wasted. [SPECULATION] For the builder's scale and stated "feel", warp-per-client (or warp-per-active-client, with thread-per-client for the homogeneous physics-ish tick) is likely the sweet spot — but this is a benchmarkable hypothesis, not a finding.

[VERIFIED] A third layout is what the field actually converged on: FLAME GPU maps **each agent to a thread and each agent *function* to a separate kernel**, stores agents **in state lists** so that a kernel only ever processes agents in the same state, and stores agent data as **Structure-of-Arrays**. Its own rationale, from Richmond's teaching material: "Avoiding diversity across agents in execution blocks — agents are stored and processed in state lists to avoid conditional branching" and "lists are stored using a Structure of Arrays (SoA) rather than an Array of Structures (AoS)". Source (index): https://slidetodoc.com/flexible-agent-based-simulation-for-pedestrian-modelling-on/

### 2.2 Common/shared state → shared memory, atomics, cooperative groups

[VERIFIED] CUDA's sharing scopes are hard-edged: shared memory is per-thread-block (fast, explicitly managed); thread-block *clusters* (compute capability 9.0+) add distributed shared memory across ≤8 portable co-scheduled blocks with hardware cluster synchronisation and atomics; grid-wide synchronisation exists only via a **cooperative launch**, which requires every block to be co-resident and therefore caps grid size at what fits simultaneously. Sources: NVIDIA CUDA Programming Guide (intro/clusters, verified via index excerpts), https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/intro-to-cuda-cpp.html.md ; cooperative-groups summary (index), https://www.aicassindra.com/blogs/gpu/cooperative_groups.html

[INFERENCE] Hence the cleanest port is **room = block**: a PLATO lesson's common (max 1,500 words ≈ 12 KB at 8 bytes/word) sits in the block's shared memory with room to spare, the room's clients are the block's threads/warps, and `__syncthreads()` is the tick barrier PLATO never needed because it was serial. The moment a "world" spans blocks, you are in global-memory + atomics + cooperative-grid territory, paying for ordering that PLATO got from its single executor thread. Design consequence: keep the unit of sharing at block scale, exactly as PLATO kept it at lesson scale; treat cross-room interaction as *messages between blocks*, not shared writes — which is also precisely PLATO's own structure (common was per-lesson; cross-lesson communication went through files/notes, not shared memory).

[VERIFIED] FLAME GPU independently arrived at the race-avoidance rule that makes shared state tractable on a GPU: agents communicate via **globally accessible message lists**; a message, once sent, is read-only for the iteration; "ensuring agents never write and read from the same message list during a single agent function gives a natural synchronisation barrier… preventing race conditions". Source (index): http://paulrichmond.staff.shef.ac.uk/test/mondus.github.io-master/cv/publications/padabs_conflict_resolution.pdf

### 2.3 Event/tick scheduling → persistent kernels, device queues, graphs, cooperative launches

[VERIFIED] Kernel launch overhead is the persistent kernel's raison d'être: reported figures cluster around **~3–10 µs per launch** (5–10 µs host overhead in the KineticSim analysis; 2.8 µs eager launch measured in the CUDA Proxy Player study). A single kernel launched once for an entire simulation, with blocks remaining resident and state cached in shared memory, removes that per-step cost and all host–device synchronisation from the loop. Sources (index): https://arxiv.org/html/2606.21784 ; https://zhhr0321.github.io/assets/img/project/CUDAproxy_rpt.pdf

[VERIFIED] But the same literature reports the counter-result, and it matters at small scale: in the CUDA Proxy Player evaluation, device-resident persistent workers pulling micro-operations from a device queue had **worker scheduling latency of 4.3 µs, *exceeding* the 2.8 µs eager launch cost**, and synchronisation barriers added ~1.25 ms per forward pass in that workload — "persistent workers currently introduce coordination overhead that cancels most of their launch avoidance benefits". Meanwhile **CUDA Graphs** capture a fixed sequence of kernels once and replay it with one launch, obtaining most of the launch saving *without* co-residency constraints — at the cost that the graph "must be constructed in full before execution" and **cannot adapt to runtime dynamics**. Device-side graph launch (CUDA 12.0+, Hopper) partially closes that gap by letting kernels schedule graph launches themselves. Sources (index): CUDA Proxy Player, above; https://openreview.net/pdf/65d90f2319af499c124a5fbe674b96367bd03d19.pdf ; NVIDIA CUDA Features Archive, https://docs.nvidia.com/cuda/archive/13.1.0/cuda-features-archive/index.html

[INFERENCE] Mapped back to PLATO: PLATO's executor corresponds not to "a kernel that never exits" but to **a scheduler that is always *available***. The GPU has three ways to buy availability — (a) persistent kernel polling a queue, (b) graph replay of a fixed tick, (c) cheap relaunches from a host loop — and PLATO's own workload (sparse, irregular, human-paced events; §1.2) is the one where (a)'s polling waste and (c)'s launch cost are *both* small in absolute terms, because events are rare. The case for (a) strengthens only when ticks are frequent and regular *and* state must stay in shared memory/registers across ticks (impossible across a kernel boundary), or when host round-trips sit on the latency-critical path for agent (non-human) clients firing thousands of events per second. That is an empirical fork the builder should measure, not a doctrine.

[VERIFIED] Persistent kernels also carry platform costs PLATO never faced: on a display-attached GPU, operating-system watchdogs (commonly ~2 s under WDDM/desktop Linux) terminate long-running kernels, and Pascal-and-later preemption, while it permits long kernels, punctures fine-grained continuous processing with gaps. Sources (index): NVIDIA developer forum, https://forums.developer.nvidia.com/t/timeout-under-linux-is-it-possible-to-remove-it/240153 and https://forums.developer.nvidia.com/t/288444.json . [INFERENCE] A "floor" kernel therefore wants a dedicated, non-display GPU (or a bounded-epoch design: kernel runs for *N* ticks or *T* ms, exits, is relaunched — by host or by device graph launch — preserving state in global memory), and this constraint should be in the design from day one, not discovered in deployment.

### 2.4 PPU/mainframe division → host, streams, and warp specialisation

[INFERENCE] The naive mapping "PPU = host CPU" inverts the interesting property. In the Cyber, the CP was the *latency* machine (one user's code, run fast, sequentially) and the PPs were *throughput/housekeeping* helpers. In CUDA, the GPU is the throughput machine and the host CPU is the latency machine. So the faithful port of PLATO's division is: **host does what the CP did** — irregular, sequential, per-client logic that must feel instant (parsing text protocols, judging free-form input, running the odd client's weird lesson) — and **the GPU does what the whole PLATO *system* did at aggregate level**: hold all the small states, apply all the uniform updates, move all the messages. A design that forces the GPU to be the CP (one persistent kernel interpreting arbitrary per-client behaviour for a handful of clients) is using the throughput machine in its worst mode and will still probably work at dozens of clients — because dozens of clients is nothing — while scaling badly in exactly the direction (more heterogeneous clients) the builder cares about.

[VERIFIED] The modern GPU-internal version of the PPU idea is **warp specialisation**: dedicate some warps of a block as *producers* (issuing asynchronous copies — `cp.async`, or TMA on Hopper — into shared-memory pipeline stages) and the rest as *consumers* (compute only), synchronising through barriers/`mbarrier`s. It is the standard structure of high-performance Hopper/Blackwell kernels (CUTLASS schedules, FlashAttention-style kernels, persistent megakernels). Sources (index): https://www.aicassindra.com/blogs/gpu/gpu_warp_specialization.html ; https://www.aicassindra.com/blogs/gpu/gpu_cutlass.html

[INFERENCE] For a room/tick floor, the specialised split worth copying is not GEMM's producer/consumer but: **one I/O warp per block** (polls the host ring buffer and the room's event queue, compacts events with ballot operations, posts outbound deltas) **plus worker warps** (tick the room). That is the PPU pattern at warp scale — housekeeping never blocks the workers, and polling divergence is quarantined to one warp.

### 2.5 What the GPU does *better* than PLATO could

[VERIFIED/INFERENCE, labelled per item]

- **True parallel update** [VERIFIED capability]: PLATO simulated simultaneity by serial round-robin service fast enough that humans could not tell; a GPU actually updates all clients in a room in the same instant, so ordering artefacts (first-come advantage inside a tick) can be designed out with double-buffering rather than inherited from service order.
- **Bandwidth and capacity** [VERIFIED]: PLATO's entire ECS plan was 2M words (~15 MB); a single current GPU holds tens of GB at TB/s-class bandwidth. The state-count ceiling that shaped every PLATO decision simply does not bind at dozens–millions of small clients.
- **Cheap fine-grained synchronisation within a block** [VERIFIED]: `__syncthreads()`, warp ballots/shuffles, and cluster barriers give per-tick rendezvous at nanosecond–microsecond scale; PLATO had no in-lesson synchronisation primitive at all.
- **Atomics and hardware queues** [VERIFIED]: contention that PLATO avoided by serialisation can be handled head-on (atomic counters, CAS-claimed ring slots — the Blink scheduler claims requests from a 4,096-slot ring by atomic CAS with a full scan in 1–5 µs; §3).
- **The display trick, generalised** [INFERENCE]: PLATO's delta-only output over 1,260 bit/s is now the default architecture of every streamed game/remote desktop; the GPU can additionally *render* the delta.

### 2.6 What PLATO did that GPUs are bad at

- **Arbitrary per-client control flow** [VERIFIED mechanism, INFERENCE application]: TUTOR's judging machinery is string matching, keyword spotting, expression evaluation and branching — per user, different every time. In SIMT that is divergence, and divergent paths serialise. Volta-and-later independent thread scheduling softens correctness hazards but does not restore the lost lanes.
- **Latency for a single client** [VERIFIED orientation]: a GPU thread is slow (in-order, hundreds of cycles of memory latency, hidden only by parallelism). PLATO's CP answered one user in a few ms *including* everything; a lone GPU client with a dependent pointer-chase pays full latency with no other warps to hide it. At very small client counts, a CPU core will beat the GPU on per-event latency for irregular work — the persistent kernel wins only by removing *launch/transfer* latency, not by making the work itself faster.
- **String/text work** [INFERENCE]: PLATO was, at heart, a text machine (answer judging, chat, notes). GPUs remain poor at byte-irregular text processing per thread; text protocols belong on the host side of the boundary (§4, nugget 7).
- **Sparseness** [INFERENCE]: PLATO's economics assumed ~zero cost for idle users. A resident persistent kernel inverts that: idle rooms still cost a spinning (or sleeping-with-wake-latency) kernel, SM occupancy denied to other work, and power. The GPU has no equivalent of "the user is just a bank in ECS" unless the design explicitly parks cold rooms out of the resident set.
- **Preemption and sharing** [VERIFIED, §2.3]: PLATO owned its mainframe. A persistent kernel on a shared/desktop GPU is a tenant with a watchdog.

**Verdict on §2 as a whole** [INFERENCE]: the mapping holds for *state layout, sharing scope, event queues, tiering, and checkpointing*; it strains for *execution semantics* (divergent interpretation, single-client latency, idle cost). The thesis's phrase "maps naturally onto SIMT" is the part that fails: it maps naturally onto the GPU's **memory system and queueing structures**, and *against the grain* of SIMT execution, which must then be managed by bucketing, warp-per-client assignment, or keeping interpretation on the host.

## 3. Cutting edge, present day: GPU-resident multi-agent simulation

### 3.1 Agent-based modelling: FLAME GPU is the state of the art, and it is not persistent

[VERIFIED] FLAME GPU 2 (Richmond et al., *Software: Practice and Experience* 2023, 53:1659–1680) is the reference framework: modellers specify agent types, agent functions and message lists in CUDA C++ or Python; the framework generates optimised CUDA; agent data stays resident on the GPU (enabling real-time visualisation); it supports multiple agent types, agent communication, and birth/death allocation. Sources (verified live): https://docs.flamegpu.com/api/page_md_README.html ; https://rse.shef.ac.uk/blog/2023-08-18-benchmarking-flamegpu2-on-h100-a100-and-v100-gpus/

[VERIFIED] Scale/latency numbers, Sheffield RSE benchmark of the FLAME GPU 2 "circles" model (single GPU, 200 steps, populations 10,648 → **1,000,000 agents**): with spatially-partitioned messaging, total time for 200 steps at 1M agents was **0.944 s (V100) / 0.685 s (A100) / 0.551 s (H100)** — i.e. roughly **2.8–4.7 ms per step for a million agents** — because each agent read on average only ~204.5 messages. With brute-force all-to-all messaging at the same population the same 200 steps took **1,456.7 s (V100)** — a ~1,500× penalty for unstructured communication. H100 vs V100 speedup at 1M agents: up to 1.75×. Source (verified live): Sheffield RSE blog, URL above.

[VERIFIED] Earlier FLAME GPU results (K40, CUDA 6) show the same shape at smaller absolute scale: a Sugarscape population of over **1M agent cells completes a simulation step in just over 5 ms; 16M cells in ~76 ms/step**, including movement conflict resolution via iterated rounds. Source (index): http://paulrichmond.staff.shef.ac.uk/test/mondus.github.io-master/cv/publications/padabs_conflict_resolution.pdf

[INFERENCE] Two transferable lessons dominate everything else in this section: (1) **communication structure, not agent count, is the scaling law** — local/spatial messaging is ~three orders of magnitude cheaper than global messaging at 1M agents; a "room" is exactly a spatial partition, which is why a room-scoped design is well-aimed; (2) the winning execution pattern is **many short kernels (one per agent function), agents pre-sorted by state, double-buffered message lists** — i.e. the field's best practice is a *discrete-step, host-orchestrated* loop, the architectural opposite of a persistent floor. Anyone building a persistent variant is, knowingly, trading the proven pattern for lower launch latency and cross-tick shared-memory residency, and should be able to say what they bought with the trade.

### 3.2 Persistent kernels and megakernels: the frontier is LLM serving, not worlds

[VERIFIED] The most active current work on persistent GPU-resident scheduling comes from LLM inference: persistent "megakernels" that fuse an entire forward pass into one launch, keep state in registers across former kernel boundaries, use warp-specialised producer/consumer CTAs resident per SM, and pull tasks from device-side queues/rings. Cohere's published megakernel serving engine, for example, uses a controller warp prefetching task descriptors into a shared-memory ring while other warps execute tasks of any opcode under a fixed thread-block shape. Sources (index): https://cohere.com/blog/megakernels ; https://theorempath.com/topics/megakernels

[VERIFIED] GPU-resident *serving* stacks go further: Blink delegates the whole LLM serving stack to a **persistent scheduler kernel (one block, 256 threads) that runs indefinitely**, scanning a lock-free ring buffer, claiming requests by atomic CAS, launching CUDA graphs device-side, and polling output buffers — explicitly so that there is "no kernel launch overhead, no host–device synchronisation, and no CPU-mediated bookkeeping on the token-critical path"; a parallel scan of all 4,096 ring slots completes in 1–5 µs. Source (index): https://arxiv.org/pdf/2604.07609 (preprint; treat performance claims as authors' own).

[VERIFIED] And the cautionary result bears repeating in this company: the CUDA Proxy Player study, which built exactly a "GPU-resident workers pull micro-operations from a device queue" system, found worker scheduling latency (4.3 µs) *above* eager launch cost (2.8 µs) and concluded that coordination/synchronisation, not launching, becomes the barrier. Grid-sync cooperative kernels have the symmetric trap: the grid barrier "is implemented through global memory and must wait for the slowest block", and co-residency limits the grid — one careful tutorial evaluation found a naive persistent global-barrier version *slower* than per-step launches (2.59 ms vs 0.89 ms at N=1k in a binomial-pricing study). Sources (index): CUDA Proxy Player, URL in §2.3; https://www.aicassindra.com/blogs/gpu/cooperative_groups.html ; https://l1-ca0.github.io/Parallel_BOPM_Report.pdf

[INFERENCE] Net assessment for a room/tick floor: persistent scheduling is a *latency* technology whose benefits are real but small in absolute terms (single-digit µs per avoided launch/handshake) and whose costs (coordination, co-residency caps, watchdog/preemption exposure, power, debuggability) are structural. It pays when events are *very* frequent relative to µs scales — token generation, market events (one persistent-kernel market simulator claims >10¹⁰ events/s; authors' preprint figure, unverified independently) — and is roughly neutral-to-negative at human event rates. Source for the market claim (index, preprint): https://arxiv.org/html/2606.21784

### 3.3 Game worlds and MMO servers on GPUs: mostly absent, and that absence is evidence

[VERIFIED, as a search result] Searches for GPU-resident MMO/game-server systems returned **no production or peer-reviewed system that runs a whole game world (clients, rooms, tick, networking) on a GPU**. What exists is: (a) ABM frameworks (§3.1); (b) GPU sub-problems for games (physics broad-phase, pathfinding, crowd simulation) — e.g. a GPU-resident BVH system claiming 60 fps collision queries for a hypothetical 1M-avatar metaverse (low-authority preprint-style source; do not rely on the number); (c) CPU-side multi-agent game environments that make the opposite point — Neural MMO simulates **128 agents on a single CPU core at ~10× real-time**, with a server tick of 0.6 s, because "MMOs are… originally designed to support small cities of players on 90s hardware" with slow internal rates and client-side animation supplying smoothness. Sources: https://arxiv.org/pdf/2001.12004 ; the BVH item is noted only to be discounted, https://freederia.com/wp-json/wp/v2/posts/564871

[INFERENCE] The pattern is consistent with §1: **worlds that feel alive have never needed much compute per client**; they need cheap state, fast event turnaround, and interpolation/presentation at the client. The GPU enters world systems where the *per-agent* work is genuinely heavy and uniform (crowds, particles, inference-driven NPC batches), not as the floor under dozens of text-protocol clients.

### 3.4 Any work explicitly connecting PLATO/mainframe design to GPU design?

[VERIFIED, as a search result] **None found.** Searches combining PLATO/TUTOR/mainframe-timesharing with CUDA/GPU/persistent kernels returned no paper, talk, or essay making the connection. The nearest genuine historical kinship is hardware-level and well documented independently: the CDC barrel processor as an ancestor of hardware multithreading (§1.7), and timesharing economics as an ancestor of cloud/GPU multi-tenancy generally. [INFERENCE] The builder's thesis therefore appears to be **original as an explicit mapping** — which cuts both ways: there is no prior art validating it, and no prior art refuting it; §2's mechanism-by-mechanism test is, as far as this research can establish, the first pass.

## 4. Design nuggets for a persistent-kernel room/tick system (dozens of clients)

Each nugget states its PLATO ancestor and its evidence. All are [INFERENCE] unless marked otherwise; none has been benchmarked in the builder's system.

**1. Make the room the thread block; make the lesson's common the block's shared memory.**
Ancestor: TUTOR `common` (≤1,500 words per lesson, shared by all users of that lesson *only*). Evidence: 1,500 words ≈ 12 KB fits modern shared memory per block with room for queues; block scope gives free tick synchronisation (`__syncthreads`) and keeps cross-room traffic as explicit messages — mirroring PLATO, where sharing never crossed lesson boundaries implicitly (§2.2). Worlds larger than a block should be *federations of rooms exchanging messages*, not one big shared array with atomics.

**2. Keep per-client state as fixed-size, flat, SoA arrays indexed by client slot — and cap it, PLATO-style.**
Ancestor: the 150-word student bank (plus fixed status words); capacity by arithmetic, no allocation. Evidence: fixed footprints are what let PLATO price 4,000 banks in ECS in advance (§1.6); on the GPU, SoA layout is the established route to coalesced access and is FLAME GPU's chosen storage (§2.1, §3.1). Split arrays by temperature: hot tick fields in SoA global (staged to shared per room), cold/profile fields in a separate AoS array touched rarely. If a client needs more state, give it a fixed "storage" extension slot (TUTOR's own `storage` command is the precedent) — never a pointer chase.

**3. Assign execution by homogeneity: thread-per-client for the uniform tick, warp-per-client for irregular per-client work, and bucket clients by state.**
Ancestor: the executor ran *one* user's condensed code at a time, so heterogeneity was free — the GPU charges for it, so you must buy it back structurally. Evidence: divergence serialises intra-warp paths (§2.1); warp-granular divergence is free (warp-specialisation literature); FLAME GPU sorts agents into state lists precisely "to avoid diversity across agents in execution blocks" (§3.1). Practical form: clients carry a state/programme tag; each tick, clients are processed in tag order (or, at dozens of clients, simply given a warp each when their tag is "interpreter-like").

**4. Be event-first, tick-second: drain event queues every cycle; tick only dirty rooms; never tick idle clients.**
Ancestor: the keypress event list (§1.2) — PLATO spent *nothing* on users between events, which is the whole reason 480 humans fit on a Cyber. Evidence: PLATO's own design documents (§1.2, §1.9); game-world practice (Neural MMO's 0.6 s tick, §3.3) shows even the tick that exists can be slow. Practical form: per-room dirty flag + event count; the resident kernel's loop is *poll queues → service events → tick dirty rooms → publish deltas → sleep/poll with backoff*, not *tick everything at fixed Hz*. Continuous ambient animation belongs to clients/renderers, as it did to PLATO's terminals and later MUD clients.

**5. Communicate inside a tick through double-buffered, append-only message lists — not through in-place shared writes.**
Ancestor: common as the inter-user medium; direct descendant in the literature is FLAME GPU's rule that agents never read and write the same message list within one function, giving "a natural synchronisation barrier… preventing race conditions" (§2.2). Evidence: that rule is what makes a million-agent step deterministic-ish and race-free (§3.1). Practical form: events/messages produced in tick *t* are visible in tick *t+1*; within-tick room state changes go through the room's single logical writer discipline (e.g. lane-0/warp-leader commits, or atomic appends to a log that is applied in slot order at the barrier).

**6. Quarantine housekeeping in dedicated I/O warps (the PPU pattern, at warp scale).**
Ancestor: PPUs ran the OS and I/O so the CP never waited (§1.7); modern form: warp specialisation (§2.4). Evidence: producer/consumer warp specialisation is the standard Hopper pattern; a polling warp also quarantines the divergent, branchy queue-management code from worker warps. Practical form: warp 0 of each room block polls the host ring and room queue, ballot-compacts arrivals, and signals via shared-memory flags/`mbarrier`; worker warps never poll global flags directly.

**7. Cross the host boundary in binary, in batches, through pinned ring buffers — keep text/JSON strictly on the host.**
Ancestor: PLATO's wire format was deliberately *not* ASCII — Sherwood & Stifle calculate ASCII would waste 25–45% overhead versus their 14%-overhead format, and that frugality is what made 1,260 bit/s viable; site controllers concentrated 32 terminals per line (§1.2). Evidence: those numbers, plus the general GPU fact that per-event host↔device round trips (µs-scale each, §2.3) dwarf the compute for dozens of clients. Practical form: host parses text protocols (the builder's tile/JSON world) into fixed-size binary event records, writes them into a pinned-memory ring with sequence numbers; the GPU polls the ring (Blink's CAS-claimed ring is the published pattern, §3.2); outbound deltas go back through a symmetric ring and are rendered to text by the host. One crossing per batch, never per keystroke-equivalent — unless a single client's latency demands it, in which case the ring is still the mechanism, just drained eagerly.

**8. Treat GPU memory as ECS, not as disk: checkpoint at tick boundaries, in persistence classes.**
Ancestor: student variables persisted across sessions *because they were kept in the student record on disk*; named common survived *because it was checkpointed from ECS to disk* (§1.4–1.6). Evidence: those mechanisms, plus the plain fact that device state dies with the kernel/context. Practical form — and here the builder's own vocabulary (§5) already has the classes: *eternal/persistent* room and client state is copied to host (pinned buffer, async on a side stream) every *N* ticks and on clean shutdown; *ephemeral* state is never copied and is understood to be reconstructible. Design the restart path (host re-uploads last checkpoint, clients re-sync) before the fast path.

**9. Budget every tick and keep PLATO's 40% reserve.**
Ancestor: the explicit ~40% capacity reserve that kept PLATO's typical wait under 0.2 s at load (§1.2). Evidence: that policy document; the cooperative-grid lesson that a barrier waits for the slowest block (§2.3) — one over-budget room stalls every room in a grid-synchronised design, which argues for *per-room* budgets and no global barrier in the normal path. Practical form: each room gets a per-tick work budget (events processed, messages scanned); overflow work is deferred to the next tick in slot order (fairness = the PPU barrel's fixed round-robin), and the system targets ≤60% occupancy of its tick interval at expected load.

**10. Prefer bounded epochs over a literally immortal kernel — unless the GPU is dedicated.**
Ancestor: none in PLATO (its executor was the OS; it owned the machine) — this nugget descends from the GPU side's evidence, included because the thesis needs it. Evidence: display-GPU watchdogs (~2 s) and preemption gaps (§2.3); persistent-worker coordination costs (§3.2). Practical form: the floor kernel runs an epoch (e.g. ≤100 ms or ≤*N* ticks), exits cleanly with all state in global memory, and is relaunched by host loop or CUDA Graph/device graph launch; cross-epoch state lives in global memory by design (nugget 2), shared memory is only a within-epoch cache (nugget 1). Benchmark epoch vs immortal on the target machine, including a second tenant workload, before committing. [SPECULATION] At dozens of clients the epoch version will very likely be indistinguishable in feel and far easier to operate.

**Failure/overflow behaviour, collected** (applies across nuggets): every queue is fixed-size (PLATO's fixed allocations again); a full inbound ring drops or coalesces *by type* (movement/presence events coalesce to latest; chat/control events are never silently dropped — they backpressure the host, which sheds load at the protocol layer where a human/agent can see it); a full outbound ring marks the client *stale* and the room sends a resync snapshot on its next slot rather than blocking the tick; a room that exhausts its budget twice consecutively is *parked* (removed from the resident set, state checkpointed — PLATO's "lesson became inactive → common deallocated", §1.5) and reactivated on its next event. No failure inside one room may take the kernel down: per-room error flags, checked by the I/O warp, are the containment unit.

## Verdict on the thesis

**Thesis as stated:** PLATO held dozens-to-hundreds of interactive users feeling dynamic on 1970s hardware using per-user state arrays, shared common state, and event/tick machinery, and that design maps naturally onto GPU SIMT execution.

- **"Dozens-to-hundreds feeling dynamic" — [VERIFIED], and understated**: it was 480 simultaneously active in 1975, designed for 1,000, at 125 ms average response of which compute was a few milliseconds.
- **"Per-user state arrays + shared common" — [VERIFIED]**, with exact sizes (150 words; 1,500 words) that turn out to fit GPU shared/global layouts almost eerily well.
- **"Event/tick machinery" — half [VERIFIED], half wrong**: the machinery was *event* machinery. There was no general tick; ticking was a game-level expedient with second-scale refresh. Importing a fixed-rate always-on tick in PLATO's name imports the one thing PLATO's economy depended on avoiding.
- **"Maps naturally onto SIMT" — fails as stated, succeeds in revised form.** The *state and queueing* design maps naturally onto the GPU's memory hierarchy and device-side queues (ECS→global, CM→shared, common→room-block shared memory, event list→ring buffer). The *execution* design — one serial interpreter running arbitrary per-user code — maps onto SIMT only after explicit anti-divergence engineering (bucketing by state, or warp-per-client), or by keeping interpretation on the host CPU, which is after all where PLATO's own "central processor" role now lives.
- **The scale mismatch cuts in the builder's favour and against the persistent-kernel choice simultaneously** [INFERENCE]: dozens of clients is 2–3 orders of magnitude below what either PLATO or a GPU can hold, so *feel* will be decided by boundary latency (host↔GPU crossings, protocol handling, presentation) — exactly the parts PLATO optimised (concentrators, frugal binary wire format, no-refresh display) and exactly the parts a persistent kernel does *not* by itself fix.

**Revised thesis that the evidence does support:** *Build the GPU floor in PLATO's image at the data layer — fixed per-client arrays, room-scoped shared state, event-first scheduling, tiered memory with checkpointing, deliberate headroom — and be un-PLATO-like at the execution layer: uniform tick code in SIMT, irregular per-client logic bucketed, warp-specialised, or left on the host. Treat persistence of the kernel itself as a measured optimisation (with bounded epochs as the default), not as the architecture.*
